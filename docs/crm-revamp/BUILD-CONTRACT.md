## Smallest additive model

Keep **`bookings` as the physical job/visit table**; avoid a parallel replacement jobs table and risky bulk rewrite. UI vocabulary can say Jobs. Keep `leads`, `intake_events`, existing quote drafts and legacy columns. Add only the structures needed for durable customer identity, properties, optional agreements, job items and separate payments. Final names/constraints are frozen by Astra before dependent work.

| Candidate | Minimum purpose and invariants |
| --- | --- |
| `customers` | UUID identity, contact fields, created/archive times. Phone is a match hint, not a unique person key. No destructive customer deletion action. |
| `properties` | UUID, customer link, submitted/display address, optional validated coordinates, reusable measurement context. Distinct properties remain distinct; do not globally deduplicate address strings. |
| Existing `leads` | Nullable customer/property links, pipeline state, follow-up time, latest contact outcome; retain intake answers/source/quote snapshots. Unknown legacy address remains readable although new intake requires address. |
| `lead_activities` | Append-only staff notes, explicit call outcomes and stage changes with actor/time. Opening tel/sms records at most an initiated action, never answered/sent. |
| `recurring_agreements` | Customer/property, active/paused/ended, start/optional end, interval unit/count, explicit next date, current service/price template. No agreement required for a one-time job. |
| Existing `bookings` | Nullable customer/property/agreement links, stable occurrence identity, separate quote acceptance if needed. Preserve UUID, dates/statuses, attribution, legacy prices/notes/screenshots/payment links. Add canceled/skipped state without deleting history. |
| `job_items` | Booking link, description/service, amount, explicit discount item or discount amount. Exact decimal money; job total is server-validated sum, never floating-point accumulation. Preserve original accepted price snapshot; future template edits do not mutate existing jobs. |
| `job_payments` | Booking link, exact amount/currency, paid date, method, provenance and operation identity; no automatic charge. Keep historical recorded amount/method/date separately recognizable if actual paid date was unknown. |
| Existing `staff_alerts` | Add channel (`voice`/`sms`), unique event + recipient + channel, provider identifier/status and attempts. Historical rows are SMS; never replay historical events into new calls. |

Use existing UUID conventions, timezone-aware event timestamps, local service dates in America/Chicago and exact money types. Index foreign keys and queried due-date/state fields. Add restrictive foreign keys, not cascading history deletion. Nullable links permit staged backfill without fabricated historical identity. Internal new tables use RLS with explicit grants: no anonymous/customer access; guarded server-only staff operations. Customer portal keeps its existing approved columns/row isolation. Security-invoker transactional functions have explicit execute grants and fixed search paths; network calls stay outside database transactions.

Before authoring migrations, read actual schema and relevant Supabase guides; discover CLI commands through help and create migration files with supported tooling. Never edit applied migrations. Supabase and Postgres skills were read for this plan, including exact money/timestamps, safe constraints, foreign-key indexes and short transactions. [Current Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) confirms grants and RLS must both be explicit. Changelog scan found upcoming legacy TLS cipher removal, not a need to change this model; implementation verifies its actual runtime/SDK compatibility.

## Shared behavior contracts

**Intake:** Existing website-map, website-manual, website-booking and website-service remain supported. A canonical submission contains stable source/submission identity, contact, required new address/property context, services, answers, consent and first/latest attribution. Preserve raw meaningful answers without leaking secrets. Save succeeds independently of downstream alert failure. Same identity/same content returns the same result; conflicting content is rejected. Canonical fixtures are not evidence of ConviFlo's wire format.

**Connector boundary:** Keep a separately testable vendor adapter mapping verified ConviFlo fields into canonical intake. Do not invent signatures, stable IDs or header support. Until an actual sanitized payload and authentication/retry contract are verified, only the canonical boundary is complete; vendor adapter and live integration status remain pending. Parent verified ConviFlo currently has nothing connected, Pixel/Webhook not set up, CAPI/Google Ads marked SOON, JSON POST/up to three retries and URL+secret controls without visible custom Authorization support. Existing Bearer/canonical route needs a verified adapter/auth compatibility solution. Parent owns read-only connector research. Google→website→CRM testing must include the new service form and delayed/revisited attribution; capture gbraid/wbraid and explicit Google campaign/ad-group/ad IDs in addition to gclid/UTMs. Account tagging is separately verified using `{campaignid}`, `{adgroupid}`, `{creative}` per the official ValueTrack mapping linked in SPINE. Do not decode gclid. Normalize Meta UTM ID macros only under an explicit source/campaign mapping; preserve generic UTMs and source-specific first/latest snapshots.

**Alert creation:** Save four channel/recipient intents for new intake, with explicit configuration for both staff. Dispatch voice and SMS concurrently after commit; durable intent survives process loss. Voice is attention-only. SMS includes contact/address/services/useful answers and available source detail, then direct protected quote URL. Use a deterministic concise summary; full answers stay in CRM. Do not wait for voice answering before text or customer success. New booking request following a previous inquiry must follow the explicit intake-event semantics and avoid accidentally treating a retry as another lead.

**Alert recovery:** Claim an intent atomically before external call. Accepted SID is not delivered/answered. Distinguish pending, sending, provider-accepted, terminal-failed and unknown outcomes; do not auto-resend unknown transport results. Reconciliation uses verified provider status or explicit review. A durable sweep/recovery invocation is part of release readiness; select a supported existing-host scheduler with parent after deployment topology is known. Request-lifetime fire-and-forget alone is insufficient. No live scheduler or notification testing now.

**Staff commands:** Every mutation requires staff authorization and returns a visible error on failure. Version/updated-time check prevents stale quote/contact overwrite. Intake/acceptance/complete/payment/generate-next operations have stable operation identity and transaction/unique protection where retried. `completeJob` marks completion and creates at most one next occurrence atomically; duplicate invocation returns the existing outcome.

**Recurring behavior:** Generate only the next actionable occurrence initially, with calendar views showing saved jobs. Interval weeks use an anchored local date; monthly uses calendar months with explicit end-of-month handling. Skip preserves an occurrence and advances; reschedule changes that occurrence without silently changing the anchor. Pause/end prevents generation and cancels future unfinished occurrences with preview. Resume requires a date. Updating agreement prices changes future generated jobs only; per-job edits are deliberate and historical prices remain inspectable.

**Money and forecasts:** Manual recorded payments remain separate from completed/accepted jobs. Preserve existing Stripe-link creation/sharing behavior without adding a new integration. New payment rows use actual paid date when supplied; never synthesize a paid date from legacy completion. Retain legacy recorded revenue and extra-charge history without counting both legacy values and imported payment rows twice. Preserve Paxton's conservative annual mowing forecast (30 visits/year) and label its assumptions, alongside any schedule-based outlook. Paused/ended agreements leave active forecast totals but stay in history. Predicted ConviFlo values remain separate, with unknown horizon until D09 is resolved.

The existing website-service browser harness already demonstrates this approach for intake, attribution, duplicate submission and simulated SMS. Extend it for the revamp rather than constructing a separate CRM application. Test scenarios include:

1. A fake Google-tagged visit submits the real local mowing/general form; first/latest source and available campaign/ad IDs reach the lead and staff alert.
2. A synthetic canonical external submission carries Meta campaign/ad-set/ad IDs, services and answers; missing fields stay unknown. This is a CRM contract test, not proof of ConviFlo compatibility.
3. Repeated/concurrent deliveries create one inquiry; captured mock requests show two voice calls and two SMS intents without contacting phones.
4. One provider call fails or times out ambiguously; the lead survives, other channels proceed and recovery avoids blind duplicates.
5. A staff member opens an alert link after session expiry, logs in, reaches the correct prefilled quote, and uses native call/text links without automatically contacting anyone.
6. A $60 one-time job becomes an $80 recurring agreement; original history remains $60, a one-visit leaf add-on stays local to that visit, and skip/reschedule/pause remain distinct.
7. Replayed completion/payment commands cannot duplicate visits or revenue; conservative forecasts and received money remain separate.
