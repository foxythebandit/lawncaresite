# Calendar and service schedules

A confirmed service schedule creates dated visits before the previous visit is done. The worker keeps a 90-day window current and catches up from the last recorded date. A week or month outside that window can be read without creating visits. The database worker runs daily at 09:00 UTC and calls reconciliation directly. An existing date collision pauses generation for the affected plan and leaves its cursor unchanged while other plans continue. Unexpected database errors roll back the worker transaction, with its cursor available for retry.

Each booking UUID remains the saved visit's identity. `occurrence_on` is its current cadence slot. `original_occurrence_on` records its original date, falling back to `occurrence_on` for older rows. Several visits can share an original date after a series moves. Virtual visits use the agreement, revision, and cadence date together. A stale revision returns a conflict before an action can resolve the slot.

A single move changes the actual date. Moving the whole plan remaps eligible cadence slots, carrying individually moved and skipped visits with their saved actual dates and states. A window-only edit keeps every date, rule segment, and generation cursor. It applies the window to the selected visit and untouched future visits while preserving individual changes, completed work and paid visits. A move that would put two visits for the same plan on one date stops before saving, including collisions with projected visits outside the 90-day window. If an existing move conflicts with a projection, the calendar shows the saved visit and flags the plan for review. A staff template price change uses the existing line-item command to update new and untouched future visits at exact cents. The migration itself keeps all existing line items. Individually edited visits, completed work, recorded payments and accepted quote snapshots stay attached to their booking IDs.

The first rollout starts generation on or after the Austin cutover date. Existing confirmed past visits stay overdue until staff records what happened. Existing monthly schedules keep their month-end clamp. A plan with no dated, identity-matched source or priced template remains available for staff review. Preferred-date requests wait for confirmation before generating future work. If the first confirmed visit is on or after the proposed second date, the agreement needs schedule review. Cutover also flags a saved move that would otherwise duplicate a regular visit. Staff can keep working with the saved visits and restart with an explicit date after them.

Staff calendar range and attention reads use private server RPCs. Today and Next 7 Days read their date ranges directly. The customer portal uses its existing ownership policy to show the nearest upcoming visit and the latest unfinished past visit. It reads completed and pending visits separately.

Use `npm run check` in the isolated local worktree. The schedule tests cover annual and temporary periods, leap-month dates, cutover preservation, missed worker runs, series shifts, stale revisions, and access grants. Native tests check the registered worker command, two concurrent reconciliation calls, an isolated schedule collision and portal ownership with real local logins. The Calendar uses those range and attention APIs.


## Calendar and visit workflow

The Calendar opens on Week at `/admin/jobs`. The date and Day, Week, or Month view are shareable. Staff sign-in restores the selected calendar view, date, and search, including the originating calendar from a visit link. A phone can scroll the week or choose a day from the strip. Visits at one property share a heading and open separate records. Exact arrival times are ordered chronologically within the timed group. Search lists visits by actual or preferred date, with undated requests after dated results. The Calendar uses the actual date for the grid, while preferred dates stay under Needs scheduling until staff confirms a visit. Overdue and Needs schedule review link to their own paged results, including detected conflicts before the daily worker records a reason. Today and Next 7 days show the same attention totals.

A visit shows its date, arrival window, price, and status before any editor opens. Mark done records completion. Payment is a separate action. Reschedule offers an explicit choice to email the customer when email is available. Notes, payment, service schedule, and contact or property details each have their own controls. The back link restores the calendar context. A calendar map loads its pins only after staff opens it.

A projected visit opens by schedule revision and date and uses the same editors as a saved visit. Viewing the page leaves the database unchanged. A deliberate visit edit saves the visit and applies the change in one database transaction. A stale revision or a saved individual change prompts staff to reopen the calendar. The operation ledger makes a retry return the same visit.

An explicit payment-link or email-reminder action prepares the saved visit before calling the existing provider. The provider request runs after commit. A retry uses the same operation key while the provider still retains it. Payment links save only against the prepared visit version, so an intervening price change prevents the old link from appearing on the visit. Missing provider configuration stops before any visit is saved. A failed provider request can leave the visit saved for staff to review.

## Browser checks

From the isolated worktree, start the feature server with `work serve daily-clarity`. Use the local staff seed. With Python Playwright and Chromium installed, run `python3 tests/daily-clarity-ui.py`. Set `QG_CALENDAR_SCREEN_DIR` to the feature’s screens directory to save captures. The test uses a local database and synthetic data. It checks Week, Day and Month at phone and desktop widths, exact visit navigation and return, notes and edit conflicts, completion and payment separately, schedule review, search, projected edits, and related staff screens. It cleans up its fixtures.

The older CRM browser scripts still target their isolated fixture server and database. Their visit selectors follow the new detail page. The dedicated calendar browser test runs against this feature worktree’s server and seed.
